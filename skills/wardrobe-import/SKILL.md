# Wardrobe 商品导入（本地优先）

主数据在 Wardrobe Local 的 SQLite。Skill 的用户编辑版本也存在 SQLite，通过 Web UI「Skills」管理；MCP 每次读取当前版本。订单文件只用作**本地导入凭据**，不作为长期主数据库，也不传给 ChatGPT、GitHub 或云对象存储。**含真实订单号的 MCP 创建工具参数同样属于会传给云端 AI 的数据**；注重隐私时应使用本地导入进程处理完整订单，只让 AI 查询必要的脱敏结果。先调用 `audit_wardrobe` 和 `search_wardrobe` 核对已有记录，不重建数据库。注意：通过云端 AI 调用 MCP 时，**MCP 响应中的字段和图片会传送到 AI 服务**；仅返回任务必要信息。

1. **订单导入默认通过已安装 Wardrobe Edge 扩展的「订单库 → 同步订单」来操作**，而非要求用户导出文件。经用户明确授权后从已登录的数据来源／数据来源订单列表观察网站正常签名的列表请求，仅在本机同步脱敏商品字段、按稳定键去重，不读取 Cookie 或账号密码、不把订单源文件发送给 ChatGPT。自动翻页只允许明确的下一页按钮（有最多 40 页上限），不声称自动覆盖所有年份或已删除订单；如站点需要重新登录、接口结构变化或出现不确定结果，应报告不足并停止。原 `/api/orders/import-file` 仅为本地兼容兜底接口，并非用户正常 UI 流程。数据来源 `optional-source endpoint` 的 `wareList` 结构已核实；数据来源真实 `optional-source endpoint` 的 `data.data[orderItemInfo*].fields.item` 结构已核实并确认可解析 30 条实际商品行。数据来源浏览器到 SQLite 的最终端到端验收仍需完成；不确定来源不视作同步成功。旧版数据来源文件行 ID 为空时，仅对同订单的唯一精确商品名称＋规格或商品 ID＋规格进行安全合并，保留人工持有状态。每笔成交行核实店铺、标题、SKU 颜色／尺码、订单号、日期、金额与退款／退货证据；缺失字段不得猜测。
2. **退款不等于退货**。数据来源「交易成功，部分退款成功」是订单层面的状态，不表示该订单下所有商品都退了。必须逐件看退款金额、退款原因与物流：`退款金额 ¥0.00` 并不构成商品退款；正数也可能是价保、补差或部分退费，不能直接判断退货。用户明确确认仍持有的商品可以记录为已持有，保留订单证据；确认为整件退货才排除。
3. 对每个订单行生成稳定唯一的 `source_key`，首选「平台:真实订单号:子订单号或行+SKU」，确保同单多商品以及重复购买可以正确区分。若旧订单仅能核验日期、店铺、SKU、价格而暂时取不到订单号，则可在用户明确要求补录时以这些真实凭据生成**标记为临时来源键**的确定性组合，订单号写「待核实」，绝不能把组合键伪装成真实订单号。此情况现有 `create_wardrobe_product` 要求真实订单号，必须使用本地受控导入事务，不得为通过校验而编造号码。先调用 `search_wardrobe` 查询同款/日期/规格，已有记录优先补充资料，禁止重复新增。
4. 证据确认且拥有真实订单号时，优先通过**本地导入程序**写入 SQLite；如果用户明确授权将对应字段发送给云端 AI，才考虑通过 MCP 调用 `create_wardrobe_product`。保存原始金额、退款状态、店铺、日期、订单核验信息至本地 `fields`。没有用户明确反馈时 `rating=0`、`ratingSource=unrated`、`fit` 待确认；`owned` 只有用户明确说仍持有时才可写为本人确认持有，其他情况待确认。正常 MCP 新建返回 `IMP-*` 编号。
5. 图片先选择真实商品详情页主图（优先实际购买颜色，必要时在数据来源 App 查看全屏大图），再用订单图、订单保障弹窗中的真实旧图或交易快照。2020 年的历史交易快照可能提示「暂无快照」，而旧图 CDN 可能 404；若仅有 200–258 像素缩略图，必须记录低清晰度待替换，不可插值放大冒充高清。由本地进程归档 JPEG/PNG 图片及真实来源；如使用 MCP 的 `save_wardrobe_image`，必须注意 **Base64 图片字节会经过发起 MCP 调用的 AI 服务**，不能将其描述为全程只在本机处理。对不希望离开本机的图片应走本地导入方式。文件不存放在仓库，不从其他商品借图，不通过 AI 放大冒充原图，不在对话粘贴完整 Base64。
6. **导入新统一订单流程**：本机 Web UI →「订单库」→选择平台与订单文件→导入→自动分类→逐件确认退款、退货、实际持有→仅将适合的商品通过「加入衣橱」关联到 `products`。原始订单 `purchase_orders` 与 `order_items` 和现有衣橱商品分离，重复导入按稳定来源键更新。浏览器 Extension 如被用户自行安装，使用浏览器原生已签名请求，仅经扩展侧边栏把白名单商品字段传到本机同源 UI 的 `/api/orders/import`；不再要求用户手动配对码，不读取 Cookie 值。订单范围要按年份/页码核对，不能把部分数据当成全量。
7. 通过 `get_wardrobe_product`、`get_wardrobe_image` 与 `audit_wardrobe` 验证商品和本地文件；报告新增/补充/排除/待核验的数量。保持其他记录、搭配、个人尺寸与发型不变。

参考 `references/order-verification.md` 处理退款和去重。用户仅请求查看资料时不得修改数据库。写入前必须有用户明确的导入授权；未知内容保持未知。


### 订单商品 → 衣橱单品 → 本地图片（自动第二阶段）

- 订单正常写入本机 `/api/orders/import` 后，自动执行 `/api/orders/organize` 建立待确认穿搭候选，但**禁止隐式调用 `/api/orders/cache-images`**。「整理穿搭入衣橱」「补齐商品图」两个独立按钮位于**衣橱**而不是订单库；用户点击整理只执行分类及关联，点击补图才分批下载 JPEG（一个 HTTP 请求一张、每次点击最多十张，后续手动点击「继续补图」）。图片来源 HTTP 失败、网络超时、格式和本地保存失败都应分别显示计数。
- 自动分类包含上衣、外套、裤装、鞋靴、袜子、保暖内搭、皮带、手套、首饰、发饰、手表、眼镜、包等；不要把服装收纳、清洁用品误算为穿搭。已退货、明确未持有不入库；退款但未退货的需人工确认，入库初始状态一律「待确认」。
- 图片优先数据来源订单 `wareList.imgPath`（优先 n0，失败回退 n1）、数据来源已购列表 `orderItemInfo.fields.item.pic`；只允许本机 Go 服务从数据来源和阿里静态图片 CDN 通过 HTTPS 限制大小下载，并以 JPEG 保存在 `Data/images/<商品ID>.jpg`。禁止伪造缺失图片或模糊匹配其他 SKU；缺图保留缺图状态，可人工用交易快照核实补录。
- 图片链接和商品名称来源由真实订单核实，不读 Cookie、请求凭证或完整 HAR，主数据库和图片绝不上传公共仓库或云端；手动分类与已有照片不得被自动更新覆盖。


### 通过 Wardrobe MCP 管理订单（本地操作）

- `get_wardrobe_order_summary` 为只读计数统计，不读取账号 Cookie 或传输原始订单，优先用于判断穿搭/图片覆盖情况。
- 经用户明确授权，调用 `organize_wardrobe_orders` 分批将来源订单商品添加为待确认持有的衣橱单品；`reconcile_wardrobe_order_duplicates` 仅在唯一的同订单、同商品 ID、同标题对应关系成立时合并历史重复行，被合并源记录归档在本机 SQLite，不能返回给云端。
- `cache_wardrobe_order_images` 只从严格白名单静态 CDN 下载真实商品图到本机 JPG，MCP 返回成功/失败数而非图片。缺失的原始交易快照、SKU 不一致或下架商品不得用近似商品代替。
- **别把已验证采集和全量历史覆盖混为一谈**：数据来源历史页可能超时，系统应报告实际覆盖数与未核实范围。不要向 ChatGPT 传入完整真实订单、私密原图或原始数据库。
